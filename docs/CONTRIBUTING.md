## Процесс работы

### 1. Подготовьте форк и upstream

```bash
# Клонировать свой форк
git clone https://github.com/YOUR_USERNAME/HobbyHub.git

# Перейти в директорию проекта
cd HobbyHub

# Добавить оригинальный репозиторий как upstream
git remote add upstream https://github.com/Zero-Logic-Education/HobbyHub.git
```

### 2. Создайте отдельную ветку

```bash
# Получить актуальные изменения из upstream
git fetch upstream

# Создать ветку от upstream/main
git checkout -b feature/short-description upstream/main
```

Допустимые префиксы веток:

<div align="center">

| **Префикс** | **Назначение** |
|:---|:---|
| `feature/*` | Новая функциональность |
| `fix/*` | Исправление ошибок |
| `docs/*` | Изменения в документации |
| `refactor/*` | Рефакторинг без изменения поведения |
| `test/*` | Тесты и тестовая инфраструктура |

</div>

### 3. Держите ветку актуальной

```bash
# Обновить ссылки на ветки upstream
git fetch upstream

# Перебазировать текущую ветку на upstream/main
git rebase upstream/main
```

## Требования к изменениям

- Один Pull Request должен решать одну задачу.
- Новая функциональность должна сопровождаться тестами.
- Если поведение изменено, документация должна быть обновлена.
- Нельзя добавлять секреты, токены, пароли, `google-services.json` и `GoogleService-Info.plist`.

### Код-стиль (кратко)

<div align="center">

| **Стек** | **Ожидание** |
|:---|:---|
| Dart / Flutter | Следовать `analysis_options.yaml`, строгая типизация, без `dynamic` без обоснования |
| Riverpod | Провайдеры локальны по scope, не хранить лишнее состояние глобально |
| Firestore | Изменения схемы согласуются с Security Rules и индексами |
| Комментарии | Объясняют причину решения, а не пересказывают код |

</div>

## Тестирование изменений

Перед PR убедитесь, что:

- `flutter analyze` проходит без предупреждений;
- `flutter test` проходит без ошибок;
- новый код покрыт тестами на уровне, достаточном для регрессий.

## Pull Requests

### Чек-лист перед открытием PR

- [ ] Ветка синхронизирована с upstream/main
- [ ] Секреты и конфигурационные файлы не добавлены
- [ ] Добавлены или обновлены тесты
- [ ] Обновлена документация при изменении поведения
- [ ] `flutter analyze` и `flutter test` проходят локально

### Шаблон описания PR

```markdown
## Описание
Что было сделано и почему

## Type of change
- [ ] Bug fix
- [ ] New feature
- [ ] Breaking change
- [ ] Documentation update

## Как проверялось
Кратко опишите сценарии проверки

## Чек-лист
- [ ] Код соответствует стилю проекта
- [ ] Добавлены нужные тесты
- [ ] Обновлена документация
- [ ] Все проверки проходят

## Related issue
Closes #123
```

### После открытия PR

1. Автопроверки CI должны быть зелёными.
2. Требуется минимум одно ревью и одобрение.
3. Замечания ревью должны быть закрыты до merge.

## Commit сообщения

Используйте формат Conventional Commits:

```text
<type>(<scope>): <subject>
```

Рекомендуемые type:

<div align="center">

| **Type** | **Назначение** |
|:---|:---|
| `feat` | Новая функциональность |
| `fix` | Исправление ошибки |
| `docs` | Изменения в документации |
| `refactor` | Рефакторинг без изменения поведения |
| `test` | Добавление или обновление тестов |
| `chore` | Служебные изменения |
| `perf` | Оптимизация производительности |
| `style` | Форматирование и визуальные правки |

</div>

Рекомендуемые scope:

<div align="center">

| **Scope** | **Примеры** |
|:---|:---|
| `app` | `ui`, `provider`, `service`, `model`, `router` |
| `firebase` | `rules`, `indexes`, `storage` |
| `infra` | `ci`, `config` |

</div>
